# 게시글 수정·삭제 실습 가이드

## 공통 규칙: 작성자 권한

수정과 삭제 모두 **로그인한 회원의 ID와 게시글의 `member_id`가 같을 때만** 허용한다. JSP에서 버튼을 숨기는 것은 편의 기능일 뿐 보안이 아니다. 반드시 Service 또는 Mapper의 `WHERE member_id = #{memberId}`로 막아야 한다.

## 1. 게시글 수정

### 권장 API

`POST /api/posts/{postId}/update`

본문은 작성과 같은 `categoryId`, `title`, `content`를 사용한다.

### 구현 순서

1. 수정 화면 진입 시 기존 글 조회 API로 값을 채운다.
2. 수정 저장 시 세션의 회원 ID를 얻는다.
3. 카테고리가 존재하는지 확인한다.
4. Mapper의 `UPDATE`에 `post_id`, `member_id`, `deleted_at IS NULL` 조건을 모두 둔다.
5. 변경 행 수가 0이면 글이 없거나 작성자가 아니므로, 학습 단계에서는 `403` 또는 `404` 중 팀 규칙을 정해 응답한다.
6. 성공 후 수정된 글을 다시 조회해 응답하고 상세 페이지로 이동한다.

### 토론할 점

작성자 여부를 먼저 `SELECT`해서 구분하면 `403`과 `404`를 정확히 나눌 수 있다. 한 번의 UPDATE 결과만 사용하면 DB 호출은 줄지만 둘을 구분하기 어렵다. 어느 방식을 택할지 이유와 함께 정해 보세요.

## 2. 게시글 삭제

### 권장 API

`POST /api/posts/{postId}/delete`

### 구현 순서

1. 로그인 여부를 확인한다.
2. `PostMapper.delete(postId, memberId)`를 호출한다.
3. SQL은 실제 행을 지우는 대신 `deleted_at = CURRENT_TIMESTAMP`로 논리 삭제한다.
4. 변경 행 수가 0이면 권한 또는 존재 여부 실패로 처리한다.
5. 성공하면 `/post/list?page=1`로 이동시킨다.

## 완료 체크

- 작성자 A는 자신의 글을 수정·삭제할 수 있다.
- 회원 B는 A의 글을 수정·삭제할 수 없다.
- 삭제된 글은 목록·상세 조회에서 보이지 않는다.
- 삭제 후 같은 글을 다시 삭제해도 성공한 것처럼 보이지 않는다.
- `updated_at`, `deleted_at` 값이 의도대로 바뀌는지 DB에서 확인한다.

## 마지막 통합 점검

1. A와 B 두 계정을 준비한다.
2. A가 question·inquiry 글을 하나씩 작성한다.
3. 목록의 필터·검색·정렬·페이지를 점검한다.
4. B로 로그인해 A 글 수정·삭제가 거절되는지 확인한다.
5. A로 로그인해 수정·삭제를 수행하고, 목록과 상세에서 결과를 확인한다.
